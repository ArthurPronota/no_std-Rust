# `no_std` в Rust 
## Что такое `no_std`

**`no_std`** — это режим компиляции Rust-программы **без стандартной библиотеки** (`std`). Вместо неё программа использует только **`core`** — минимальное подмножество языка, не зависящее от операционной системы.

Включается атрибутом в начале крейта:

```rust
#![no_std]
```

---

## Иерархия библиотек Rust

Rust поставляет **три уровня** библиотек:

| Библиотека | Что содержит | Зависит от ОС? | Аллокация? |
|---|---|---|---|
| **`core`** | Примитивы, `Option`, `Result`, итераторы, арифметика | ❌ Нет | ❌ Нет |
| **`alloc`** | `Vec`, `String`, `Box`, `Rc`, `Arc`, коллекции | ❌ Нет (нужен аллокатор) | ✅ Да |
| **`std`** | `core` + `alloc` + файлы, потоки, сеть, время | ✅ Да | ✅ Да |

```
┌─────────────────────────────────────┐
│              std                    │  ← полный набор, зависит от ОС
│  ┌─────────────────────────────┐    │
│  │           alloc             │    │  ← куча, но без ОС
│  │  ┌─────────────────────┐    │    │
│  │  │       core          │    │    │  ← самый минимум
│  │  └─────────────────────┘    │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
```

**`no_std`** означает «не подключать `std`». При этом `core` доступен **всегда**, а `alloc` — только если вы явно его подключите и предоставите глобальный аллокатор.

```rust
#![no_std]

extern crate alloc;  // опционально, если нужны Vec/String/Box
```

## Что становится недоступно

| Возможность | `std` | `no_std` |
|---|---|---|
| `println!`, `eprintln!` | ✅ | ❌ |
| `std::io` (файлы, stdin/stdout) | ✅ | ❌ |
| `std::thread` | ✅ | ❌ |
| `std::fs` | ✅ | ❌ |
| `std::net` | ✅ | ❌ |
| `std::time` | ✅ | ❌ |
| `String`, `Vec`, `Box` | ✅ | ⚠️ Только через `alloc` + свой аллокатор |
| `HashMap`, `BTreeMap` | ✅ | ⚠️ Через `alloc` |
| `core::option::Option`, `Result` | ✅ | ✅ |
| `core::slice`, `core::str` | ✅ | ✅ |
| Итераторы, замыкания, трейты | ✅ | ✅ |
| Обработчик паники по умолчанию | ✅ | ❌ (нужен свой) |
| Точка входа `main` по умолчанию | ✅ | ❌ (нужен `#![no_main]`) |

## Что нужно определить вручную

При `#![no_std]` компилятор требует от вас несколько вещей:

### 1. Обработчик паники

```rust
use core::panic::PanicInfo;

#[panic_handler]
fn panic(_info: &PanicInfo) -> ! {
    loop {}  // или ExitProcess(1) на Windows
}
```

Без него линковка упадёт с ошибкой `#[panic_handler] function required`.

### 2. Точку входа (если `#![no_main]`)

```rust
#[no_mangle]
pub extern "C" fn mainCRTStartup() -> ! {
    // ...
}
```

Имя зависит от платформы и линкера: `_start` (Linux), `mainCRTStartup` (Windows console), `WinMainCRTStartup` (Windows GUI).

### 3. Глобальный аллокатор (если нужен `alloc`)

```rust
use alloc::alloc::{GlobalAlloc, Layout};

struct MyAllocator;

unsafe impl GlobalAlloc for MyAllocator {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 { /* ... */ }
    unsafe fn dealloc(&self, ptr: *mut u8, layout: Layout) { /* ... */ }
}

#[global_allocator]
static ALLOC: MyAllocator = MyAllocator;
```

### 4. Обработчик `alloc_error_handler` (в nightly)

На stable этот шаг не требуется — по умолчанию аллокация при нехватке памяти вызывает `panic`.

## Где применяется `no_std`

### 1. Встраиваемые системы (embedded)

Микроконтроллеры (STM32, ESP32, AVR, RISC-V) **не имеют ОС**. `std` там просто не существует. Примеры крейтов:

- `embedded-hal` — абстракции над периферией
- `cortex-m`, `riscv` — доступ к ядру
- `defmt`, `panic-halt` — отладка и паника
- `heapless` — коллекции без аллокатора

### 2. Ядра операционных систем

Redox OS, ядра на Rust — пишутся в `no_std`, потому что `std` сам зависит от ОС.

### 3. Bootloaders (загрузчики)

Программа, которая выполняется **сразу после включения питания** и готовит систему к запуску ОС. У неё ещё нет ни ОС, ни `std`. Пример: `bootloader` crate для x86.

### 4. WASM-рантаймы и sandbox-среды

WASM-модули часто компилируются без ОС-зависимостей, чтобы работать в браузере или в изолированной среде.

### 5. Криптографические библиотеки

`ring`, `dalek` и подобные часто пишутся в `no_std`, чтобы работать и в embedded, и в ядре, и в userspace.

### 6. Минимальные утилиты

Когда критичен **размер бинарника** — например, ваша программа на Windows. `no_std` даёт ~3–8 КБ вместо ~150 КБ.

## Особенности `no_std`

### Нет `std::io`, `std::thread`, `std::fs`

Работу с файлами, сетью и потоками нужно делать через **прямые системные вызовы** (на Linux) или **Windows API** (на Windows).

### Нет `println!`

Вывод в консоль — вручную:

- **Linux**: `write(1, buf, len)` через `syscall`
- **Windows**: `GetStdHandle` + `WriteConsoleA` (как в вашем коде)

### Нет паники по умолчанию

Нужен `#[panic_handler]`. Обычно он либо завершает процесс, либо уходит в бесконечный цикл (в embedded), либо мигает светодиодом.

### Аллокатор

Часто **отсутствует** вообще. Тогда:

- **статические буферы** фиксированного размера;
- **`heapless`** — коллекции с фиксированной ёмкостью (`Vec<T, N>`, `String<N>`);
- либо свой аллокатор на арене / пуле.

### Нет `main`

Точку входа задаёт линкер, а вы объявляете её через `#[no_mangle]`.

## Пример: минимальный `no_std` для Windows

Ваш код — классический пример:

```rust
#![no_std]                  // без std
#![no_main]                 // без автоматического main
#![windows_subsystem = "console"]  // консольное приложение

use core::ffi::c_void;
use core::panic::PanicInfo;
use windows_sys::Win32::System::Console::{GetStdHandle, WriteConsoleA, STD_OUTPUT_HANDLE};
use windows_sys::Win32::System::Threading::ExitProcess;

#[cfg(not(test))]
#[panic_handler]
fn panic(_: &PanicInfo<'_>) -> ! {
    unsafe { ExitProcess(1) }
}

#[allow(non_snake_case)]
#[unsafe(no_mangle)]
fn mainCRTStartup() -> ! {
    let message = "Hello, world!\n";
    unsafe {
        let console = GetStdHandle(STD_OUTPUT_HANDLE);
        WriteConsoleA(
            console,
            message.as_ptr().cast::<c_void>(),
            message.len() as u32,
            core::ptr::null_mut(),
            core::ptr::null(),
        );
        ExitProcess(0)
    }
}
```

Здесь:
- **`core`** даёт `PanicInfo`, `c_void`, указатели.
- **`windows-sys`** даёт доступ к Windows API без `std`.
- **`ExitProcess`** заменяет `std::process::exit`.
- **`WriteConsoleA`** заменяет `println!`.

## Преимущества `no_std`

| Преимущество | Пояснение |
|---|---|
| **Минимальный размер** | Нет линковки с `std` — бинарник 3–8 КБ |
| **Нет скрытых зависимостей** | Вы контролируете каждую функцию |
| **Работает без ОС** | Embedded, ядро, bootloader |
| **Предсказуемость** | Нет фоновых потоков, аллокаций «под капотом» |
| **Быстрый старт** | Нет инициализации `std` |

---

## Недостатки `no_std`

| Недостаток | Пояснение |
|---|---|
| **Сложность** | Много `unsafe`, ручная работа с API |
| **Нет удобств** | `println!`, `Vec`, `String` — вручную или через `alloc` |
| **Мало крейтов** | Большинство библиотек требуют `std` |
| **Платформенная специфика** | Код под Windows не соберётся под Linux без правок |
| **Сложная отладка** | Нет `backtrace`, `dbg!`, удобных сообщений паники |

## Итог

| Вопрос | Ответ |
|---|---|
| Что такое `no_std`? | Режим без стандартной библиотеки, только `core` (+ опционально `alloc`) |
| Как включить? | `#![no_std]` в начале крейта |
| Что нужно определить? | `#[panic_handler]`, точку входа, при необходимости — аллокатор |
| Где применяется? | Embedded, ядра ОС, bootloaders, WASM, минимальные утилиты |
| Зачем? | Минимальный размер, работа без ОС, полный контроль |
| Цена? | Сложность, отсутствие удобств, много `unsafe` |

**Одной фразой**: `no_std` — это режим Rust без стандартной библиотеки, дающий минимальный бинарник и работу на «голом железе», но требующий вручную определять панику, точку входа и (при необходимости) аллокатор.
